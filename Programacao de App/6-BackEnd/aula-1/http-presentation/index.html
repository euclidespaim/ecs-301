Fundamentação Teórica

O que são Métodos HTTP?

O protocolo HTTP (Hypertext Transfer Protocol) baseia-se em um modelo de Requisição e Resposta (Client-Server). Toda comunicação se inicia com o cliente enviando uma mensagem de solicitação ao servidor.

O Método HTTP (frequentemente chamado de Verbo HTTP) é o primeiro elemento da linha de requisição. Ele indica a ação semântica que se deseja realizar no recurso identificado pela URL.

Analogia: Se o recurso (URL) é um substantivo (ex: /clientes), o Método HTTP é o verbo que indica o que fazer com ele (ex: GET para ler, POST para criar).
Anatomia de uma Requisição HTTP
POST /usuarios HTTP/1.1
Host: api.exemplo.com
Content-Type: application/json
Content-Length: 37

{
  "nome": "João",
  "cargo": "Dev"
}

A linha superior define a ação (POST), o alvo (/usuarios) e o protocolo (HTTP/1.1).

Propriedades dos Métodos

Métodos Seguros & Idempotentes

🛡️

Método Seguro (Safe)

É um método que não altera o estado do recurso no servidor (operação de apenas leitura). Ele pode ser executado sem gerar efeitos colaterais.

GET HEAD OPTIONS
🔄

Método Idempotente

A execução repetida da mesma requisição produz o mesmo efeito colateral no servidor que uma única execução. Fazer a chamada 1 ou 100 vezes deixa o servidor no mesmo estado final.

GET PUT DELETE HEAD OPTIONS

Por que isso importa?

Entender essas propriedades é vital para o desenvolvimento de APIs eficientes e robustas:

  • Cache: Métodos seguros podem ser cacheados pelo navegador ou proxies para acelerar a navegação.
  • Tratamento de Falhas: Conexões de rede oscilam. Se uma requisição idempotente falha por timeout, ela pode ser reenviada automaticamente de forma segura sem duplicar dados.
  • CORS: O navegador trata métodos não seguros com cuidado redobrado (disparando requisições OPTIONS prévias).
💡 Analogia da Idempotência: Pense no botão de chamada de um elevador. Apertá-lo 1 ou 10 vezes produz o mesmo efeito final: o elevador virá uma única vez. No HTTP, reenviar uma requisição idempotente (como PUT ou DELETE) após uma falha de rede é seguro. Reenviar um POST (não-idempotente), porém, criaria registros duplicados.
Métodos de CRUD (Leitura e Escrita)

GET vs. POST

GET

Leitura (Read)

  • Objetivo: Solicitar e ler dados de um recurso.
  • Seguro e Idempotente: Sim. Não altera dados no servidor.
  • Corpo (Body): Não possui (semântica padrão).
  • Parâmetros: Enviados na própria URL (Query Params).
    /busca?termo=backend
  • Cache: Altamente cacheável.
  • Caso de uso: Listar produtos, ver perfil de usuário.
POST

Criação (Create)

  • Objetivo: Enviar dados para criar um novo recurso.
  • Seguro e Idempotente: Não. Executar duas vezes criará dois registros.
  • Corpo (Body): Sim. Contém o payload a ser salvo (ex: JSON).
  • Parâmetros: Ocultos na URL, passados no Body.
  • Cache: Não cacheável.
  • Caso de uso: Realizar cadastro, enviar formulários, fazer login.
Métodos de CRUD (Edição e Exclusão)

PUT vs. PATCH vs. DELETE

PUT

Substituição Completa

Substitui todo o recurso identificado na URL pelos dados enviados. Se faltar algum campo na requisição, esse campo será removido ou resetado.

Idempotente: Sim Corpo: Obrigatório
PUT /usuarios/1
→ Atualiza todo o cadastro do usuário 1.
PATCH

Modificação Parcial

Aplica alterações parciais no recurso. Envia-se apenas o atributo que se deseja modificar, preservando os demais atributos intactos.

Idempotente: Não (geralmente) Corpo: Obrigatório
PATCH /usuarios/1
→ Altera apenas a senha ou foto do perfil.
DELETE

Exclusão de Recurso

Remove o recurso especificado na URL. Uma vez deletado, novas requisições costumam retornar status 404 (Não Encontrado).

Idempotente: Sim Corpo: Opcional/Raro
DELETE /usuarios/1
→ Apaga a conta do usuário 1 permanentemente.
Métodos Auxiliares e de Segurança

HEAD & OPTIONS

HEAD

Apenas Cabeçalhos

Funciona exatamente como o GET, mas o servidor não retorna o corpo (Body) da resposta. Retorna apenas a linha de status e os cabeçalhos HTTP.

Principais Casos de Uso:

  • Verificar se um link de download está online e ativo.
  • Checar o tamanho do arquivo (Content-Length) ou tipo de arquivo antes de baixá-lo.
  • Checar se o recurso foi modificado usando o cabeçalho Last-Modified ou ETag.
OPTIONS

Opções de Comunicação

Retorna os métodos HTTP e recursos suportados pelo servidor para determinada URL, sem iniciar a ação real.

Principais Casos de Uso:

  • CORS Preflight: Navegadores disparam automaticamente uma chamada OPTIONS antes de chamadas complexas (POST, PUT, DELETE) para garantir que o domínio externo autoriza a operação.
  • Descobrir quais verbos um endpoint suporta (ex: se aceita ou não DELETE).
Métodos de Diagnóstico e Infraestrutura

CONNECT & TRACE

CONNECT

Túnel de Rede TCP/IP

Estabelece um túnel de comunicação direta bidirecional com o servidor identificado pelo recurso de destino. É utilizado principalmente por navegadores para passar conexões seguras criptografadas (HTTPS) através de servidores proxy não criptografados.

TRACE

Loopback e Depuração

Solicita ao servidor que retorne exatamente a mensagem de requisição recebida no corpo da resposta. É um teste de loopback que permite verificar se proxies intermediários, firewalls ou roteadores alteraram cabeçalhos da requisição original.

O método CONNECT estabelece um túnel seguro de ponta a ponta sem que o Proxy intermediário intercepte os dados criptografados.
